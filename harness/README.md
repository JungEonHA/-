# AI 스튜디오 하네스 — 정보 인테이크 안내

AI 에이전트 9 + 사람 2 로 굴러가는 숏드라마 / AI 인플루언서(IP) 스튜디오를
Claude Code 하네스로 세우기 위해, **어떤 정보를 어떤 형태로 주면 되는지** 정리한 문서다.

- 채워 넣을 질문지: [`INTAKE.md`](./INTAKE.md)
- 해상도 기준이 되는 예시: [`EXAMPLE-agent-contract.md`](./EXAMPLE-agent-contract.md)

## 0. 먼저 — 흔한 함정 세 가지

정보를 주기 전에 이것부터 합의하는 편이 낫다. 여기서 어긋나면 뒤에 준 정보가 전부 헛돈다.

### ① 사람 조직도를 그대로 복사하지 않는다

"마케팅 팀장", "PD", "기획실장" 같은 직책은 **사람들 사이의 커뮤니케이션 비용** 때문에
생긴 구조다. 에이전트는 그 비용 구조가 다르다. 팀장 에이전트를 만들면 할 일이 없거나,
아랫 에이전트가 만든 걸 다시 만든다.

에이전트는 **산출물 경계**로 나눈다. 기준은 하나다 — *"이 에이전트가 넘겨주는 파일이
정확히 무엇인가?"* 에 한 줄로 답이 나와야 한다.

| 나쁜 분할 | 좋은 분할 |
| --- | --- |
| 콘텐츠 팀장 | 에피소드 대본 `.md` 를 내놓는 에이전트 |
| 마케팅 담당 | 썸네일 3안 + 제목 5안 을 내놓는 에이전트 |
| 운영 지원 | 업로드 후 24시간 지표를 표로 적는 에이전트 |

### ② "매일 자율적으로"의 병목은 지능이 아니라 상태와 승인이다

에이전트가 똑똑해서 자율적인 게 아니라, **어제 뭘 했는지 읽을 곳이 있어서** 자율적이다.
그래서 인테이크에서 가장 답이 중요한 항목은 E 블록(회사의 기억)과
D 블록의 **"사람이 12시간 답이 없으면 어떻게 하는가"** 다.

### ③ 사람 2명은 검수자가 아니라 거부권자로 설계한다

9명이 만든 걸 2명이 전수검사하면, 그 2명이 즉시 병목이 된다. 자동화한 의미가 없어진다.

- 사람이 **반드시** 봐야 하는 것: 되돌릴 수 없는 행동 — 대외 공개, 지출, 계약, 대외 발언
- 사람이 **표본만** 보는 것: 품질 (예: 하루 산출물 중 무작위 2건)
- 사람이 **안 보는 것**: 나머지 전부. 대신 기준(G 블록)을 문서로 준다

즉 인테이크에서 필요한 건 "사람이 뭘 검수하나"가 아니라
**"사람이 안 봐도 나가도 되는 것의 경계가 어디인가"** 다.

## 1. 준 정보가 하네스의 어디로 가는가

정보를 준다는 건 결국 아래 파일들을 채우는 일이다. 미리 알고 있으면 정보의 형태를 맞추기 쉽다.

```
CLAUDE.md                     회사 헌법 — 모든 에이전트가 매번 읽는다        ← A, G 블록
.claude/
  agents/                     에이전트 9명의 계약서 (1인 1파일)              ← C 블록
    scriptwriter.md
    art-director.md
    ...
  skills/                     반복 SOP — "썸네일 만드는 법" 같은 절차서       ← B 블록
  commands/                   사람이 부르는 슬래시 명령 (/오늘 /승인 /긴급)   ← D 블록
  settings.json               권한·훅 — 자동 게이트와 금지선                  ← D, F 블록
company/
  pipeline.md                 아이디어 → 공개까지의 단계와 산출물             ← B 블록
  brand/                      IP 별 페르소나·톤·금지선·레퍼런스               ← G 블록
  state/  (또는 Notion)       회사의 기억 — 일지·결정 로그·작업 큐            ← E 블록
```

**매핑 규칙 한 줄 요약**

| 준 정보 | 되는 것 |
| --- | --- |
| 하지 말아야 할 것 | 훅 / 권한 설정 (물어보지 않고 막힘) |
| 반복되는 절차 | 스킬 |
| 누가 무엇을 만드는가 | 에이전트 정의 |
| 언제 시작하는가 | 스케줄 트리거 |
| 어디에 적는가 | 상태 저장소 (Notion DB 또는 레포 파일) |
| 사람이 부르는 말 | 슬래시 명령 |

## 2. 정보의 품질 순서

같은 내용이라도 형태에 따라 가치가 10배 차이 난다.

| 순위 | 형태 | 왜 |
| --- | --- | --- |
| 1 | **실제 산출물 원본** — 잘 나온 대본 1편, 실제 업로드된 영상, 실제 Notion DB CSV | 기준을 말로 옮기다 생기는 손실이 없다 |
| 2 | **실패 사례** — 최근에 엎은 것, 반응이 죽었던 것, 그 이유 | 금지선은 성공 사례로 못 만든다 |
| 3 | **실제 하루 로그** — 어제 두 사람이 몇 시에 뭘 했는지 | 리듬과 병목이 그대로 드러난다 |
| 4 | 화면 캡처 (Notion DB 구조, 폴더 트리, 사용 툴 화면) | 스키마를 추측하지 않아도 된다 |
| 5 | 말로 쓴 설명 | 있어야 하지만, 위의 것 없이 이것만 있으면 추측이 섞인다 |

**"잘 정리해서 드릴게요"는 대체로 늦어진다.** 정리 안 된 원본이 정리된 요약보다 낫다.
날것으로 던지고, 정리는 이쪽에서 한다.

## 3. 진행 순서 — 9명을 한 번에 만들지 않는다

9명을 한 번에 정의하면 전부 어설프게 된다. 파이프라인 한 줄기를 먼저 완주시킨다.

| 단계 | 하는 일 | 필요한 블록 | 걸리는 시간 |
| --- | --- | --- | --- |
| 1차 | 회사 헌법 + 파이프라인 문서 + 상태 저장소 뼈대 | A, B, E | 인테이크 1회 |
| 2차 | **에이전트 2~3명만** 실제로 세워서 하루 돌려본다 | C (그 3명분), G | 답 받고 바로 |
| 3차 | 사람 2명의 승인 경로 · 슬래시 명령 · 알림 연결 | D | 2차가 돌아간 뒤 |
| 4차 | 나머지 6명 확장 + 스케줄 자동화 | C (나머지), H | 3차 안정화 후 |
| 5차 | 지표 수집 → 다음 사이클 피드백 루프 | F, H | 데이터가 쌓인 뒤 |

2차에서 고를 3명은 **가장 병목인 구간** 으로 고른다. 가장 쉬운 구간이 아니다.

## 4. 지금 당장 답장으로 보낼 수 있는 최소 6가지

[`INTAKE.md`](./INTAKE.md) 전체를 채우려면 오래 걸린다. 아래 6개만 먼저 주면 1차를 시작할 수 있다.

1. **지금 운영 중인 채널/IP** 목록과, 하루 또는 주 단위로 만들어야 하는 산출물 개수
2. **아이디어 → 업로드까지 실제로 거치는 단계**를 순서대로 (쓰는 툴 이름까지)
3. **에이전트 9자리에 지금 생각 중인 직무명 9개** (틀려도 됨, 여기서 같이 다시 나눔)
4. **사람 두 분이 각각 누구고, 무엇만은 반드시 직접 결정해야 하는지**
5. **기록이 지금 어디에 쌓이는지** — Notion DB 이름들, Drive 폴더 구조, 파일명 규칙
6. **잘 나온 결과물 1~2개 + 최악의 실패 1개** (링크 또는 파일)

이 6개면 A·B·E 블록이 채워지고 하네스 뼈대가 선다.
나머지는 돌려보면서 채우는 편이, 미리 완벽하게 쓰는 것보다 정확하다.
